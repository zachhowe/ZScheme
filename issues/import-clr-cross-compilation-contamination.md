# `import-clr` validation contaminated by process-wide reflection scan across unrelated compilations

**Found by:** fuzzer run, seed `0x912140c6`, 1000 iterations
(`fuzz-runs/20260701-065416-seed912140c6/`)

**Affects:** 85 of 93 failures in this run — 79 "both backends failed to
compile", 3 "IL only failed", 3 "C# only failed" (all `compile`-oracle
failures).

**Representative seeds:** `e150123a` (both fail), `9de1f191` / `26badb4c` /
`2ce487e4` (IL-only fail), `528136a5` / `dd852b12` / `ff3b5a08` (C#-only fail).

Repro:
```
dotnet run --project src/ZScheme.Fuzzer -- --repro fuzz-runs/20260701-065416-seed912140c6/artifacts/fuzz-failure-e150123a/original.zs
```

## Symptom

Every one of these cases fails type inference with an `import-clr` binding
"parameter count/return type mismatch" error against a **user-defined class
generated by the same program**, e.g.:

```
import-clr binding 'call-c0-m0-0' (ZSchemeFuzzed.FCls_0.M0_0) does not match the CLR
member: parameter count mismatch: declared 3, actual expects 1.
Declared (FCls_0 Int Int -> Int), actual (ZSchemeFuzzed.FCls_0 -> Int).
```

The declared arity always matches what's actually in the `.zs` source (i.e.
the *program is valid*), but the "actual" signature reported doesn't match
anything in the source at all — it looks like it's being validated against a
different program's class entirely.

## Root cause

[TypeInferer.cs](src/ZScheme.Compiler/Types/TypeInferer.cs) validates
`import-clr` annotations by resolving the target member through
[`ClrInterop.FindType`](src/ZScheme.Compiler/Codegen/ClrInterop.cs:1332) /
`FindTypeForMember`, both of which scan **`AppDomain.CurrentDomain.GetAssemblies()`**
— i.e. every assembly currently loaded anywhere in the process — rather than
anything scoped to the current compilation.

The fuzzer generates every case under the **same fixed namespace**
(`ZSchemeFuzzed`, from `CompilerOptionsFactory`) with the **same deterministic
class-naming scheme** (`FCls_0`, `FCls_1`, `M0_0`, …), and runs many cases
concurrently in one process. `DifferentialExecOracle` loads each case's
compiled output into a *collectible* `AssemblyLoadContext` to execute
`Compute()` — but those assemblies remain visible to
`AppDomain.CurrentDomain.GetAssemblies()` until GC'd. So while case A's
assembly is still loaded, a concurrently- or subsequently-running case B whose
program also declares a class named `FCls_0` with a method `M0_0` can have its
own (perfectly correct) `import-clr` self-reference validated against case
A's unrelated `FCls_0.M0_0` — a false compile error, and a *non-deterministic*
one, since it depends on which other cases happen to still have assemblies
loaded in the process at that moment. That non-determinism is exactly what
produces the "IL only failed" / "C# only failed" split: the two
`CompileConsistencyOracle` sub-compiles run at slightly different times, so
they can observe a different process-wide assembly set.

This is not fuzzer-only collateral damage — it's a genuine compiler
correctness bug: **`ClrInterop`'s reflection-based validation of `import-clr`
bindings is not scoped to the current compilation**, so any long-running host
process that compiles multiple ZScheme programs with colliding type names (a
language server, a REPL, or this fuzzer) can have one compilation's
`import-clr` checks silently validated against a completely unrelated,
previously-loaded type. The existing comment at
[TypeInferer.cs:1951](src/ZScheme.Compiler/Types/TypeInferer.cs:1951) already
acknowledges assembly-graph conflicts are possible in a long-running host
(citing OmniSharp) but only guards against reflection *exceptions* — it does
not guard against reflection *silently succeeding against the wrong type*,
which is the failure mode here.

## Suggested fix direction

Scope `FindType`/`FindTypeForMember` (or the caller in `TypeInferer`) so that
self-referential lookups against types declared by the *current* compilation
never fall through to the process-wide `AppDomain` scan — e.g. resolve
same-compilation class/record/union types from the AST's own symbol table
first, and only fall back to `AppDomain.CurrentDomain.GetAssemblies()` for
genuinely external CLR types.

## Priority note

Highest priority of the three findings from this run: it's a real correctness
bug in the shared front end (not fuzzer noise), and it's the reason 85/93
"failures" from this run are not independently informative — until it's
fixed, the fuzzer's compile-consistency signal is noisy for any two cases
that reuse class names in the same process.
